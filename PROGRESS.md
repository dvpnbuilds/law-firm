## Phase 3: Intake conversation — built
Notes:
- Scripted-with-flex state machine (`lib/ai/intake.ts`) drives steps description → name → email → phone → done, persisted in `lexintake_intakes.details.step` (Zod schema `lib/schemas/intake.ts`).
- Classification (`lib/ai/classify.ts`): OpenRouter chat call constrained to JSON output, Zod-validated, one retry, falls back to `other` on repeated failure/parse error (RULES.md rule 7 — never persists unvalidated output; `other` maps to a human-handoff status rather than a guess).
- `other` classification sets `case_type_id: null` and, once contact info is collected, final `status: "handoff"` instead of `"completed"` — satisfies PLAN.md's other→human-handoff routing while still producing a complete record.
- Mid-conversation FAQ switch: any non-description-step message containing `?` is routed to the existing `faqAnswer` (Phase 2, guardrail still enforced) instead of being consumed as the scripted answer; reply is the FAQ answer + a "back to your intake" resume prompt for the current step, then the same step is re-asked on the next turn. No extra LLM call needed for the switch itself (heuristic, consistent with guardrail.ts's regex-only approach).
- `lib/db/intakes.ts` + `lib/db/messages.ts` added following the existing `lib/db/*` repository pattern (no inline Supabase queries elsewhere — rule 8).
- Single API route `POST /api/intake/message` (Zod-validated via `lib/schemas/intake.ts`) creates an intake on first call (`intakeId: null`) and continues it thereafter; both user and assistant turns persisted to `lexintake_messages`.
- Widget at `/widget`: client component chat UI, static greeting, posts to `/api/intake/message`, locks input on `complete`.
